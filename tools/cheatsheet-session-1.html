3 · Вправа 1 — наслідки зміни колонки

10 хвилин. Тільки каталог db/, база не потрібна.

Ми плануємо змінити тип CO.PRODUCTS.PRODUCT_ID.

Третій пункт — головний. «Знайшов усе» нічого не варте без опису, чому ви так вважаєте.

Знайди всі місця, яких це торкнеться, і для кожного поясни, що саме зламається.

Окремо напиши, як ти перевірив, що нічого не пропустив.
можна працювати і без Claude — просто grep. Але спробуйте порівняти

Дві вʼюхи — PRODUCT_ORDERS і CUSTOMER_ORDER_PRODUCTS. Вони стануть INVALID і перекомпілюються при першому зверненні — тобто зміна пройде успішно, а впаде вночі, у звіті. Це найважливіше тут.
А тепер цікаве. Словник даних знає про три залежні вʼюхи:

Тобто текстовий пошук буває завузьким (регістр), а словник — заширшим. Правильна відповідь потребує обох: словник дає кандидатів, читання коду — хто з них справді торкається колонки.

5 · Ізоляція — спробуйте зламати по-справжньому

Щоб перевірка щось означала, спершу створіть у своїй схемі таблицю, яку сусід спробує прочитати. Інакше «не існує» нічого не доводить — його не існує й так.

крок 1 — створіть у себе
create table my_probe (x number);
insert into my_probe values (42);
commit;
select count(*) from my_probe;
у власній схемі ви можете все
очікується — таблиця створена, 1 рядок. Скажіть сусідові свій логін.
крок 2 — спробуйте прочитати таблицю СУСІДА
select count(*) from ЛОГІН_СУСІДА.my_probe;
підставте реальний логін: TRAINEE1…TRAINEE5
очікується відмова
ORA-00942: table or view does not exist
Ви точно знаєте, що таблиця є — сусід щойно її створив. Oracle каже «не існує», а не «немає доступу»: навмисно, щоб не можна було вивідати склад бази.
крок 3 — спроба записати у спільну схему
create table hr.probe (x number);
очікується відмова
ORA-01031: insufficient privileges
HR і CO видані лише на читання.
прибрати за собою
drop table my_probe purge;

7 · Домашнє завдання №1

Візьміть повільний запит — свій робочий або по схемі SH (918 843 рядки в SH.SALES). Знайдіть причину повільності, виправте і доведіть покращення.

Оцінюється не «чи стало швидше», а чим ви це довели. Час виконання не приймається: ми всі на спільній базі через _low, тому час залежить від сусідів. Логічні читання і форма плану — ні.

план виконання
explain plan for
select p.product_name, sum(oi.quantity * oi.unit_price)
  from co.order_items oi
  join co.products p on oi.product_id = p.product_id
 group by p.product_name;

select * from table(dbms_xplan.display(null, null, 'BASIC'));
приклад на CO — на своєму запиті робіть так само
очікується
-------------------------------------------
| Id  | Operation           | Name        |
-------------------------------------------
|   0 | SELECT STATEMENT    |             |
|   1 |  HASH GROUP BY      |             |
|   2 |   HASH JOIN         |             |
|   3 |    TABLE ACCESS FULL| PRODUCTS    |
|   4 |    TABLE ACCESS FULL| ORDER_ITEMS |

план із реальною статистикою виконання
select /*+ gather_plan_statistics */ count(*) from sh.sales;

select * from table(dbms_xplan.display_cursor(format => 'ALLSTATS LAST'));
саме цей формат показує фактичні рядки проти оцінених
очікується — таблиця плану з колонками E-Rows і A-Rows. Велика різниця між ними — типова причина поганого плану.

  from v$mystat m
