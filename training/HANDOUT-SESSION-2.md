# Сесія 2 — робочий листок

Claude Code для Oracle-розробки · 2 години

**Сьогоднішній результат:** власний набір правил і перевірений рефакторинг одного
PL/SQL-пакета. На Сесії 1 ми визначали, що інструмент бачить. Сьогодні визначаємо,
за якими правилами він працює і чим підтверджує результат.

Тримайте поруч [контракт лабораторії](session-2/lab/SPEC.md).

- [ ] Python 3.10+, SQLcl і Claude Code доступні.
- [ ] `sql -S -name train` підключає вас до **власного** навчального облікового запису.
- [ ] `lab/install.sql` виконано; `lab/verify-baseline.sql` видав `BASELINE_CONFIRMED`.
- [ ] Відкрито `lab/SPEC.md`; видно файли `.claude/skills/` і `.claude/agents/`.
- [ ] Створено теку `artifacts/` для результатів.

Після появи чи зміни конфігурації hook перезапустіть Claude Code в цій робочій теці.

## Наш кейс

У власній схемі є `S2_ORDERS`, `S2_ORDER_ITEMS` і пакет `S2_SETTLEMENT`:

| Функція | Контракт |
|---|---|
| `order_total(p_order_id number)` | сума позицій замовлення |
| `merchant_due(p_order_id number)` | виплата продавцю за правилами статусу та комісії |

Комісія — **1,5%**: для `COMPLETE` виплата дорівнює
`ROUND(order_total(p_order_id) * 0.985, 2)`. Правила суми, помилок і статусів
записано у специфікації; вона є джерелом вимог до коду.

| Замовлення | Статус | Загальна сума | Виплата |
|---|---|---:|---:|
| 1001 | COMPLETE | 25,55 | 25,17 |
| 1002 | CANCELLED | 99,99 | 0,00 |
| 1003 | COMPLETE | 0,30 | 0,30 |
| 1004 | COMPLETE, без позицій | 0,00 | 0,00 |
| 1005 | COMPLETE, дві позиції по 0,34 | 0,68 | 0,67 |

Невідоме замовлення — помилка `-20001`, порожній ідентифікатор `NULL` — `-20002`.
Нульова сума і відсутнє замовлення — різні результати.

Функції читають власні незбережені зміни поточного підключення. Вони не змінюють
дані та не виконують `COMMIT` чи `ROLLBACK`: транзакцією керує код, який їх викликає.

Початковий пакет компілюється, але навмисно порушує частину контракту.
Завдання — знайти й виправити порушення, зберігши публічні сигнатури та правильні випадки.

## 0–10 · Пригадаємо, що є доказом

Тренер показує підготовлену пару звітів:

> **А:** «Пакет скомпілювався, сума 1001 правильна. Готово».
>
> **Б:** «Ось контракт, перевірки звичайного, скасованого, порожнього і невідомого
> замовлення, фактичний вивід та перелік того, що я ще не перевірив».

Запишіть у `artifacts/recap.md` дві речі, яких бракує звіту А для рішення про готовність.
Це підготовлений приклад заняття, а не результати попередніх робіт учасників.

## 10–30 · Skill: повторювана інструкція

**Мета:** отримувати рев'ю за однаковим правилом, із перевірюваними посиланнями.

1. Відкрийте `.claude/skills/oracle-lab-review/SKILL.md`.
2. Знайдіть: коли застосовувати, які джерела читати, який формат результату.
3. Запустіть skill у Claude Code:

```text
/oracle-lab-review lab/settlement.pkb.sql
Перевір S2_SETTLEMENT за lab/SPEC.md.
Працюй лише з файлами; код і тести поки не змінюй.
Для кожного висновку наведи файл, місце в коді, вимогу специфікації
та приклад, який покаже проблему. Неперевірене познач окремо.
```

4. Додайте до skill **одне конкретне правило рев'ю**, яке випливає зі специфікації
   або ваших стандартів. Не додавайте нову бізнес-вимогу до пакета.
5. Повторіть рев'ю та порівняйте відповіді. Збережіть їх у `artifacts/skill-review.md`.

**Спостережуваний результат:** знайдене порушення має зв'язок
«вимога → код → перевірка». Фраза «варто покращити обробку помилок» без прикладу
ще не є достатнім результатом.

## 30–45 · Subagent: окремий перевіряльник

**Мета:** дати окремому агенту обмежену задачу й отримати компактний результат.

```text
Використай subagent oracle-reviewer для незалежного рев'ю S2_SETTLEMENT.
Передай йому lab/SPEC.md, lab/settlement.pks.sql, актуальний
lab/settlement.pkb.sql і потрібні файли перевірок.
Завдання: знайти порушення контракту, не редагувати файли та не виконувати SQL.
Попроси повернути висновки з доказами, відсутні дані й запропоновані перевірки.
Порівняй результат із artifacts/skill-review.md: де вони збігаються,
де відрізняються і що потрібно перевірити виконанням.
```

Збережіть у `artifacts/agent-review.md` **три колонки**: висновок, доказ, дія для перевірки.
Перевірте, що Claude справді викликав окремого агента. Якщо замість виклику він лише
описав можливий результат, це ще не виконана вправа.

**Спостережуваний результат:** інший контекст породжує окреме рев'ю;
узгодженість двох відповідей сама по собі не доводить правильність коду.

## 45–60 · Hook: програмне правило

**Мета:** відрізнити інструкцію для моделі від перевірки події інструмента.

Відкрийте `.claude/settings.json` і файли `.claude/hooks/`. Знайдіть подію,
інструмент, який вона охоплює, і команду запуску перевірки.

1. До запуску запишіть, який дозволений приклад має пройти і який заборонений має
   бути відхилений.
2. Запустіть локальну демонстрацію hook:

   ```bash
   python .claude/hooks/demo.py
   ```

3. Порівняйте очікування з повідомленням і кодом завершення.
4. Назвіть хоча б один шлях, який це правило **не охоплює**.

Очікуються сім рядків `PASS`: шість сценаріїв і перевірка, що тимчасовий SQL-файл
не змінився. Дозволені `Write SELECT` і `Edit SELECT` повертають код `0`;
заборонені приклади та неповний вхід — `2`. Сама демонстрація завершується кодом `0`.

Результат — `artifacts/hook-check.md`: вхід, очікування, факт, межа застосування.
Негативний приклад подається в hook як тестові дані; небезпечну команду виконувати
не потрібно. Тест перевіряє саму програму hook. Окремо тренер покаже, чи підключена
вона в поточній сесії Claude Code. Hook охоплює `Write`/`Edit` SQL-файлів у `lab/`;
він не перехоплює SQLcl, Bash, MCP чи ручне редагування. Коментарі й рядки також
можуть спричинити хибне блокування.

## 70–85 · Оркестрація: поділ роботи й один висновок

**Мета:** організувати кілька перевірок, об'єднати результат і прийняти рішення.

```text
Підготуй план виправлення lab/settlement.pkb.sql за lab/SPEC.md, без редагування.
Доручи oracle-reviewer перевірити бізнес-контракт і обробку помилок.
Сам перевір, які вимоги покриті lab/verify.sql і які граничні випадки він перевіряє.
Ці читання можна виконати паралельно. Дочекайся результату агента.
Об'єднай висновки у таблицю: вимога, поточна поведінка, доказ, зміна, перевірка.
Відокрем факти, припущення й пункти, для яких потрібен запуск Oracle.
```

Збережіть результат у `artifacts/plan.md`. Погоджений план має визначати,
**які файли змінюються і які результати залишаються правильними**.
Одночасні агенти в цій вправі читають файли; зміну пакета виконує один агент.

## 85–105 · Специфікація → зміна → перевірка

Перед зміною запустіть повну перевірку й збережіть вивід:

```bash
sql -S -name train @lab/verify.sql
```

На стартовому пакеті помилка перевірки **очікувана**. Відрізняйте її від помилки
підключення: у виводі мають бути результати самих перевірок контракту.

```text
Виконай artifacts/plan.md. Виправ lab/settlement.pkb.sql за lab/SPEC.md.
Збережи публічні сигнатури. Специфікацію, тестові очікування і fixture-дані не змінюй.
Прибери дублювання обчислення суми, збережи обумовлене округлення,
не приховуй неочікувані помилки.
Покажи diff. Скомпілюй зміни командою sql -S -name train @lab/compile.sql.
Потім запусти sql -S -name train @lab/verify.sql.
У підсумку відокрем: що змінив, що виконав, фактичний результат, що не перевірив.
```

Перевірте diff, команду й схему. Компіляція застосовує поточний
`lab/settlement.pkb.sql` і перевіряє помилки; очікується `COMPILE_OK`.
Повна послідовність після зміни:

```bash
sql -S -name train @lab/compile.sql
sql -S -name train @lab/verify.sql
```

**Ознака виконання:** `ACCEPTANCE_PASS: checks=18, unexpected=0`, незмінені перевірки й контракт,
збережений вивід у `artifacts/verification.txt`. Повторний `install.sql`
не призначений для розгортання вашої зміни; `reset-starter.sql` повертає дефектний
старт у БД, але не перезаписує ваш робочий файл. Незмінний зразок
`lab/settlement-starter.pkb.sql` під час вправи не редагують.

## 105–115 · Міст до великої системи

У `artifacts/context-map.md` опишіть аналогічну задачу для умовних 250 000 об'єктів:

| Питання | Що записати |
|---|---|
| Як починаємо пошук? | компактний індекс об'єктів і критерій відбору |
| Що читаємо далі? | лише потрібні сигнатури, тіла, DDL і залежності |
| Якого контексту може бракувати? | динамічний SQL, зовнішні виклики, права, неявні правила |
| Що доручаємо окремо? | обмежена перевірка із заданим результатом |
| Чим закриваємо задачу? | перевірки контракту, незмінених результатів і рев'ю diff |

Це навчальна схема підходу. Вона не є готовою картою системи банку.

## Якщо щось не працює

| Ситуація | Як продовжити |
|---|---|
| Claude Code недоступний | прочитайте skill і agent-файл як інструкцію, зробіть рев'ю вручну; hook-тести запускаються локально |
| Oracle недоступний | працюйте зі специфікацією, файлами та планом; у підсумку напишіть «компіляція й виконання не перевірені» |
| Hook не видно у сесії | перевірте робочу теку та перезапустіть Claude Code; локальний тест hook залишається доступним |
| Лабораторія вже встановлена | прочитайте повідомлення; якщо потрібен чистий старт і роботу збережено, використайте `lab/reset-starter.sql` |
| На проблему пішло понад 2 хвилини | працюйте в парі з сусідом і збережіть власний аналіз |

Не позначайте вправу перевіреною лише тому, що очікувані числа надруковані в цьому
листку. Потрібен фактичний результат запуску вашого пакета.

## Офіційні Oracle skills

[Oracle Skills](https://github.com/oracle/skills) містить домен `db/` із матеріалами
для бази даних, PL/SQL і SQLcl. Перед застосуванням прочитайте призначення skill,
його джерела й примітки про сумісність із Oracle 19c.
Локальний `/oracle-lab-review` додає конкретні правила нашої навчальної задачі.

Для окремого ознайомлення після заняття офіційний README наводить такі команди Claude Code:

```text
/plugin marketplace add oracle/skills
/plugin install db@oracle-skills
```

Вони встановлюють зовнішній плагін у вашому середовищі. Для виконання лабораторії
встановлення не потрібне. Джерело й команди перевірено 15 вересня 2026 року:
[інструкція Oracle](https://github.com/oracle/skills#install-in-claude-code).
