# Домашнє завдання №2 — правило, яке працює повторно

Claude Code для Oracle-розробки · після Сесії 2

**Результат:** один власний skill **або** hook для повторюваної задачі та докази,
що він працює в потрібних межах. Оберіть один варіант і доведіть його до кінця.

Працюйте на синтетичному прикладі. Лабораторія `S2_SETTLEMENT` підходить;
можна вигадати інший невеликий приклад зі своєї практики.

---

## Варіант A · Власний skill

Приклади задач: рев'ю контракту PL/SQL, перевірка сум і округлення, підготовка
плану зміни колонки, перевірка SQL-звіту за незалежним джерелом.

### Що зробити

1. Напишіть одним реченням, **коли** skill потрібен і який результат видає.
2. Визначте мінімальний контекст: специфікація, потрібний DDL, код, перевірки.
3. Створіть `.claude/skills/<назва>/SKILL.md` із чіткими інструкціями та форматом відповіді.
4. Випробуйте його на двох підготовлених прикладах:
   - **Позитивний:** код або запит відповідає вашому правилу. Skill має підтвердити
     перевірені пункти з посиланнями на докази й не вигадати порушення.
   - **Негативний:** ви навмисно внесли одне порушення. Skill має знайти саме його,
     показати місце та пояснити наслідок.
5. Додайте приклад **браку контексту**: що skill має попросити або позначити як
   неперевірене, якщо йому не дали специфікацію чи потрібну таблицю.

Назвіть приклади й запишіть очікувану відповідь **до** запуску. Збережіть фактичні
відповіді окремо. Формулювання відповіді може змінюватись; оцінюйте зміст і докази.

## Варіант B · Власний hook

Оберіть вузьке правило, яке можна перевірити програмно: наприклад, відхиляти
конкретну небезпечну форму команди або вимагати певний атрибут інструментального виклику.

### Що зробити

1. Опишіть подію, вхідні дані, правило й поведінку при порушенні.
2. Додайте код hook, конфігурацію підключення та локальні тестові вхідні дані.
3. Перевірте щонайменше:
   - **Позитивний випадок:** дозволена операція проходить.
   - **Негативний випадок:** заборонена операція відхиляється з поясненням.
   - **Граничний випадок:** неправильний або неповний вхід; очікувана поведінка визначена.
4. Запишіть команду перевірки, фактичний результат і коди завершення.
5. Опишіть, **що цей hook не охоплює**. Наприклад, перевірка тексту Bash-команди
   не аналізує SQL усередині файла і не перехоплює звернення через інший інструмент.

Негативні випадки перевіряйте подачею тестових даних у hook. Для доказу блокування
не потрібно виконувати руйнівний SQL чи команди над справжніми файлами.

## Що має бути в результаті

| Файл або розділ | Вміст |
|---|---|
| `README.md` | проблема, коли запускати, потрібний контекст, точні кроки відтворення |
| Skill або hook | робочий файл; для hook також конфігурація підключення |
| `examples/` | синтетичний позитивний і негативний приклади; очікування до запуску |
| `evidence/` | фактичні відповіді skill або результати тестів hook |
| Межі | неперевірені припущення, відомі обмеження та необхідна перевірка людиною |

**Формат передачі:** Pull Request у навчальний репозиторій до власної теки
`homework/session-2/<ваш-ідентифікатор>/`. Якщо GitHub недоступний, підготуйте ту саму
теку локально; вона має відтворюватися без вашого усного пояснення. Дату завершення
узгоджують окремо.

Не додавайте wallet, паролі, токени чи робочі дані банку. Конфігурація повинна
посилатися на особисте збережене з'єднання, якщо воно взагалі потрібне для прикладу.

## Критерії готовності

| Критерій | Бали | Що є доказом |
|---|---:|---|
| Конкретна повторювана задача | 2 | зрозумілий тригер і корисний результат |
| Інструкція або програмне правило | 2 | можна повторити запуск за README |
| Позитивний і негативний приклади | 2 | є очікування та фактичний результат обох |
| Контекст і межі | 2 | зазначено потрібні джерела, невідоме та шляхи обходу правила |
| Перевірюваність результату | 2 | знайдене порушення прив'язано до коду або тест має однозначний результат |

**Готово: 8 із 10 балів або більше**, причому позитивний і негативний приклади
обов'язкові. Робочі секрети чи дані замінюють синтетичними перед передачею.

Обсяг файла не оцінюється. Коротке правило, яке стабільно вирішує одну задачу,
корисніше за довгу інструкцію без способу перевірити результат.
