# Стандарти лабораторії сесії 2

Ці правила описують навчальний кейс. Бізнес-контракт і точні приклади містяться
в `lab/SPEC.md`; при розбіжності звіряй висновок із цією специфікацією.

## Контракт і арифметика

- Збережи публічні функції `S2_SETTLEMENT.order_total(p_order_id)` та
  `S2_SETTLEMENT.merchant_due(p_order_id)` і їхню специфікацію пакета.
- `order_total` повертає суму вартостей позицій замовлення. Підсумуй повну
  точність `quantity * unit_price`, без проміжного чи підсумкового округлення
  цієї функції. Для замовлення без позицій сума дорівнює нулю.
- Комісія становить 1,5%. `merchant_due` повертає округлений до двох знаків
  добуток `order_total(p_order_id) * (1 - 0.015)`. Не округляй комісію окремо
  і не підсумовуй округлені виплати за позиціями.
- Для замовлення `CANCELLED` виплата продавцю дорівнює нулю;
  `order_total` усе одно обчислює суму позицій.
- Невідоме замовлення породжує `RAISE_APPLICATION_ERROR(-20001, ...)`,
  `NULL` як ідентифікатор — `-20002`. Обидві функції мають цей контракт.
  Нульовий і від'ємний ідентифікатори, яких немає в даних, є невідомими.
- Для грошових обчислень використовуй Oracle `NUMBER`, не `BINARY_FLOAT`.
  Назви змінних мають розрізняти суму замовлення, ставку і виплату.

## SQL і доступ

- Працюй тільки з власними `S2_ORDERS`, `S2_ORDER_ITEMS` та `S2_SETTLEMENT`.
  Кваліфікатори чужих схем і звернення до банківських даних тут не потрібні.
- Для відомих таблиць використовуй статичний SQL і PL/SQL параметри.
  Не конкатенуй значення параметрів у SQL. Якщо динамічний SQL обґрунтовано
  потрібен в іншому кейсі, значення передавай через bind-змінні `USING`.
- Обчислення сум виконуй SQL-агрегацією. Не роби окремий запит для кожної
  позиції; не замінюй це вимогою фіксованої кількості запитів без вимірювання.
- Перевір існування замовлення окремо від агрегату: `SUM` без `GROUP BY`
  повертає рядок із `NULL` і не піднімає `NO_DATA_FOUND`.
- Пакет лише читає дані: без `INSERT`, `UPDATE`, `DELETE`, DDL,
  `COMMIT`, `ROLLBACK`, автономних транзакцій або зміни сесії.
  Інсталяційні та seed-скрипти мають іншу роль; не приписуй їм обмеження
  read-only, встановлене для функцій пакета.
- Розгортання виконується під навчальним користувачем у його схемі.
  Для stored PL/SQL права на чужі об'єкти, видані лише через роль,
  не замінюють прямі grants. Цей кейс спеціально використовує власні таблиці.

## Помилки, зміни та докази

- Не приховуй помилки через `WHEN OTHERS THEN RETURN 0/NULL`.
  Очікуваний `NO_DATA_FOUND` перетвори на контрактну помилку в потрібному
  блоці; не маскуй інші збої під «замовлення не знайдено».
- Збережи API та бізнес-семантику; змінюй лише код, потрібний для контракту.
  Не додавай механізми кредитування, податків чи реальні реквізити.
- Критерії приймання: пакет `VALID`, порожній `USER_ERRORS`, контрольні суми,
  округлення на межі половини копійки, порожнє та скасоване замовлення,
  невідомий і `NULL` ідентифікатори для обох функцій; дані й транзакція
  виклику залишаються незміненими.
- Розрізняй очікуваний результат, статичний висновок і фактичний SQL-лог.
  Називай тест пройденим лише після відповідного запуску.
