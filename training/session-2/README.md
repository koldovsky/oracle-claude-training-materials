## Підготовка робочої теки

Потрібні Python **3.10+**, Git, SQLcl, Claude Code і особисте збережене з'єднання SQLcl
`train` із Сесії 1. Зовнішні бібліотеки Python для підготовки теки не потрібні.

Із кореня репозиторію або розпакованого ZIP:

```bash
python training/session-2/setup-workspace.py
cd training/session-2/workspace
```

Команда створює окрему теку з `lab/`, активними `.claude/`, `.mcp.json` і
`CLAUDE.md`, а також окремий Git-репозиторій із початковим комітом для перегляду diff.
Тренерський еталон `trainer/` у неї не потрапляє. Якщо тека вже існує,
скрипт відмовляється її перезаписувати. Для ще одного прогону вкажіть іншу назву:

```bash
python training/session-2/setup-workspace.py training/session-2/workspace-rehearsal
```

Цю альтернативну команду також виконують **із кореня репозиторію або ZIP**. Нова локальна
тека не створює нову схему Oracle: стан бази визначає з'єднання `train`.

Якщо у вашій системі Python 3 запускається як `python3`, використовуйте цю назву
замість `python` в усіх командах матеріалів. Створена конфігурація hook використовує
саме той інтерпретатор, яким ви запустили підготовку робочої теки.

## Перший запуск лабораторії

Усі наступні команди — з `training/session-2/workspace/`:

```bash
sql -S -name train @lab/install.sql
sql -S -name train @lab/verify-baseline.sql
claude
```

`install.sql` створює лише власні навчальні об'єкти `S2_ORDERS`, `S2_ORDER_ITEMS`,
пакет та службове маркування лабораторії. Підтримуються навчальні облікові записи
`TRAINER`, `TRAINEE1`…`TRAINEE5`. Скрипт відмовляється замінювати наявні об'єкти
лабораторії. Спільні HR, CO і SH для вправи змінювати не потрібно.

**Ознака правильного старту:** `BASELINE_CONFIRMED`. Це підтверджує відому поведінку
навмисно дефектного стартового пакета. Це ще не означає виконання контракту.

## Команди під час заняття

| Дія | Команда або точка входу |
|---|---|
| Рев'ю за правилами | `/oracle-lab-review` у Claude Code |
| Окремий перевіряльник | попросіть Claude використати `oracle-reviewer` |
| Локальна демонстрація hook | `python .claude/hooks/demo.py` |
| Компіляція зміненого тіла пакета | `sql -S -name train @lab/compile.sql` |
| Повна перевірка контракту | `sql -S -name train @lab/verify.sql` |
| Повернення до початкового стану | `sql -S -name train @lab/reset-starter.sql` |
| Прибирання власної лабораторії після роботи | `sql -S -name train @lab/cleanup.sql` |

Повна перевірка стартового пакета **має завершитися помилкою**. Після виправлення
очікується `ACCEPTANCE_PASS`. Не змінюйте специфікацію, тестові очікування чи
перевірочні скрипти, щоб отримати цей результат.

**Змінюйте `lab/settlement.pkb.sql`.** `lab/compile.sql` застосовує саме цей файл
і перевіряє помилки компіляції; очікується `COMPILE_OK`. Публічна специфікація
`lab/settlement.pks.sql` і початковий зразок `lab/settlement-starter.pkb.sql`
залишаються незміненими.

`reset-starter.sql` відновлює початкові рядки й пакет **у БД**, використовуючи
незмінний `settlement-starter.pkb.sql`. Ваш робочий `settlement.pkb.sql` він не
перезаписує: наступний `compile.sql` знову розгорне його поточний вміст.
`cleanup.sql` видаляє марковані об'єкти лабораторії у власній схемі.
Ці команди виконують свідомо, а не як автоматичний крок діагностики.

Кожен основний SQL-скрипт запускають окремою наведеною командою: після роботи
він завершує процес SQLcl. У цих підключеннях не повинно бути іншої незавершеної
роботи. Перевірки додають власні тимчасові дані й відкочують їх.

## Необов'язково · запуск через Python для автоматизації

У Windows-автоматизації можна використати `run-lab.py`: він явно задає порожній
стандартний ввід SQLcl, встановлює правильну робочу теку й перевіряє результат.
**Наведені команди виконуються з кореня репозиторію або ZIP**, а не з `workspace/`:

```bash
python training/session-2/run-lab.py baseline
python training/session-2/run-lab.py compile
python training/session-2/run-lab.py verify
```

За замовчуванням використовується `training/session-2/workspace/` і з'єднання
`train`. Для іншої робочої теки:

```bash
python training/session-2/run-lab.py verify --workspace training/session-2/workspace-rehearsal --connection train
```

Доступні дії: `install`, `baseline`, `compile`, `verify`, `reset`, `cleanup`.
Вони запускають відповідні SQL-скрипти з тими самими змінами й обмеженнями,
що описані вище. Успіх потребує нульового коду SQLcl, відсутності повідомлень
про помилки та очікуваного маркера; додатково друкується `SQLCL_RUN_PASS <дія>`.
На дефектному стартері `verify` має завершитися помилкою, тоді як `baseline`
підтверджує відомий початковий стан.

## Що залишається після заняття

У робочій теці створіть `artifacts/` і збережіть:

1. результати skill і окремого агента з посиланнями на код;
2. очікування та фактичний результат демонстрації hook;
3. короткий план зміни за специфікацією;
4. виправлений файл пакета і вивід повної перевірки;
5. схему мінімального контексту для аналогічної задачі у великій системі.

**Межа підтвердження:** перевірка Python перевіряє локальні інструменти підготовки;
перевірка Oracle перевіряє скомпільований пакет; виклик через Claude Code перевіряє
ланцюг Claude → SQLcl → Oracle. Один результат не замінює решту.
