# Специфікація: розрахунок виплати продавцю

Це синтетична навчальна модель, натхненна схемою CO. Дані й код розміщені у власній схемі учасника. HR, CO та SH лабораторія не змінює. Правила нижче — умови вправи, а не правила реальних банківських розрахунків.

## Модель

- **S2_ORDERS**: order_id — ключ; status — COMPLETE або CANCELLED.
- **S2_ORDER_ITEMS**: ключ (order_id, line_no); quantity > 0; unit_price >= 0; зовнішній ключ на замовлення.
- Числові обчислення виконуються з Oracle NUMBER. Проміжну суму не округлюємо.
- Замовлення може не мати жодної позиції. Це коректний випадок із сумою 0.

## Незмінний публічний інтерфейс

    function order_total(p_order_id number) return number;
    function merchant_due(p_order_id number) return number;

Обидві функції належать пакету S2_SETTLEMENT. Специфікацію пакета, назви функцій, параметр і тип результату зберігаємо.

**order_total** повертає SUM(quantity * unit_price) для всіх позицій існуючого замовлення. Для порожнього замовлення повертає 0. Статус CANCELLED не змінює суму позицій.

**merchant_due** для COMPLETE повертає ROUND(order_total * 0.985, 2): комісія становить 1,5%. Для CANCELLED повертає 0.

Обидві функції:

1. Для NULL піднімають помилку -20002.
2. Для невідомого order_id піднімають помилку -20001.
3. Не маскують інші помилки нулем. Текст повідомлення може бути зрозумілим українським; контракт перевіряє код.
4. Не виконують DML, COMMIT, ROLLBACK або автономних транзакцій. Керування транзакцією належить виклику.
5. Бачать власні незбережені зміни поточного підключення та не змінюють дані.

## Детерміновані фікстури

| order_id | Статус | Позиції | order_total | merchant_due |
|---|---|---|---:|---:|
| 1001 | COMPLETE | 2 × 10.00 + 1 × 5.55 | 25.55 | 25.17 |
| 1002 | CANCELLED | 1 × 99.99 | 99.99 | 0 |
| 1003 | COMPLETE | 3 × 0.10 | 0.30 | 0.30 |
| 1004 | COMPLETE | немає | 0 | 0 |
| 1005 | COMPLETE | 1 × 0.34 + 1 × 0.34 | 0.68 | 0.67 |

Для 1005 округлення комісії окремо для кожної позиції дало б виплату 0.66. Правильний результат 0.67 отримуємо лише з округленням загальної виплати.

ID 1999 зарезервовано для тимчасової перевірки транзакції. ID 999999 використовується як невідомий.

## Робочий цикл

Запускайте кожен основний скрипт в окремому SQLcl-підключенні TRAINER або TRAINEE1..5, з кореня підготовленого робочого каталогу Сесії 2: у ньому є тека lab. Наприклад, зі збереженим підключенням train:

    sql -S -name train @lab/install.sql
    sql -S -name train @lab/verify-baseline.sql

Якщо тренер запускає скрипти з кореня вихідного навчального репозиторію, у цих командах слід замінити префікс @lab/ на @training/session-2/lab/.

Встановлення створює таблиці, фікстури та тіло settlement-starter.pkb.sql. Якщо у схемі вже є будь-який об'єкт S2_, install.sql зупиняється до змін. Він не перезаписує попередню роботу.

Початкова версія компілюється, але порушує контракт. verify-baseline.sql підтверджує саме її очікувану поведінку: 18 перевірок, 5 позначок KNOWN_FAIL і підсумок BASELINE_CONFIRMED. Це означає, що дефекти відтворені; це не приймання рішення. Несподіваний результат дає ненульовий код завершення SQLcl.

Редагуйте робочий файл settlement.pkb.sql у своїй гілці. Він спочатку містить ту саму початкову реалізацію. Файл settlement-starter.pkb.sql залиште незмінним: він потрібен для повторюваного відновлення. Після кожної зміни:

    sql -S -name train @lab/compile.sql
    sql -S -name train @lab/verify.sql

Критерій приймання: пакет без помилок у USER_ERRORS, усі 18 перевірок пройшли, підсумок ACCEPTANCE_PASS. verify.sql на початковій версії має завершитися помилкою з п'ятьма невідповідностями. Числові результати перевіряємо точним порівнянням NUMBER.

Тести додають замовлення 1999 без COMMIT, перевіряють видимість змін, незмінність рядків і збереження SAVEPOINT; потім відкочують лише свої тестові рядки. Запускайте їх в окремому навчальному підключенні без іншої незавершеної роботи: помилкове рішення може порушити транзакцію, а SQLcl завершує невдалу перевірку з ROLLBACK.

## Повернення до початку

    sql -S -name train @lab/reset-starter.sql
    sql -S -name train @lab/verify-baseline.sql

reset-starter.sql перевіряє позначки лабораторії, видаляє всі рядки двох її таблиць, відновлює фікстури й початкове тіло пакета з settlement-starter.pkb.sql. Він не змінює робочий файл settlement.pkb.sql. Спочатку збережіть свої зміни у git.

Після завершення вправи:

    sql -S -name train @lab/cleanup.sql

cleanup.sql спочатку перевіряє позначки всіх цілей і видаляє лише S2_SETTLEMENT, S2_ORDER_ITEMS та S2_ORDERS; індекси й обмеження цих таблиць видаляються Oracle разом із ними. Повторне очищення порожньої лабораторії безпечне. Непізнані однойменні об'єкти блокують очищення.

install.sql, compile.sql, reset-starter.sql і cleanup.sql виконують DDL або COMMIT. Запускайте їх в окремому підключенні без іншої незавершеної транзакції. Основні скрипти завершують процес SQLcl після виконання, тому кожну команду запускайте окремо. Службові файли з префіксом підкреслення призначені для виклику через основні скрипти.
